# Open decisions

Working rule: no item here is settled by inference. When one is needed, it is put to Ahmed with the options.
Reference country: Algeria. Phases: A (a complete free platform), B (user feedback and improvement), C (legal, subscriptions and payments) — see `docs/mvp-roadmap.md`.

| Q14 | A dedicated SMTP provider (such as Resend or Brevo) and a domain for correspondence. The Supabase free tier refuses custom e-mail templates with the default mailer, limits the number of messages, and the default templates work with PKCE links that open only in the same browser | Needed for trilingual messages (the templates are ready in `supabase/templates/`), for links that work from any device, and for inviting real users | Before the closed trial (S7) | **Recommendation:** Resend (3,000 messages/month free) with a domain of the platform's own; once activated, restore the e-mail templates in `config.toml` then `npm run db:config:push` |
| Q15 | The support channel (e-mail or form) and the fate of the content of a content creator whom support returned to Student: does it remain editable by its owner or does it freeze (it stays published either way)? | The `support.email` setting is empty now and "the support channel will be announced soon" is shown; the content edit policy does not check the role at present | Before the first real return (S2–S4) | **Recommendation:** a support e-mail on the platform's domain, and freezing content edits for whoever returned to Student while it stays published and attributed to them |
| Q16 | A permission matrix configurable by the owner (which capability for each rank) instead of fixed in `capabilities.ts` and the database functions | Requires a `rank_capabilities` table read in `getSession` and in the SQL functions together so the two layers never differ | When custom delegation to a moderator or an administrator is actually needed | **Recommendation:** keep the fixed matrix at this stage; the four ranks with their limits from the specification are enough until S4 |
| Q17 | Importing a `.lisanpkg` package from outside the platform (a file a content creator writes themselves or exports from another platform) | Widens the sources of content quickly, but opens an attack surface: large files, paths outside the root, assets with a forged type | When the first content creator asks for it (S2 or later) | **Recommendation:** authoring inside the platform for now; import opens after the validator and the size limits are complete (ADR 0006) and with review, because every imported package is untrusted input |
| Q18 | Upgrading a plugin schema: what happens to published packages when a new `schema_version` is released? | A published package must not break, and the content belongs to its owner, not to the platform | At the first incompatible change in a plugin (after S2) | **Recommendation:** the plugin keeps reading its old schemas forever, and the upgrade is optional by decision of the package owner with a new version of it; no forced upgrade and no silent edit of anyone's file |
| Q19 | Indexing the text of package items for internal search (an index table unpacked at publication) | Search currently runs on metadata only (R7); a learner may search for a word inside a lesson | If the feedback in phase B shows a real need | **Recommendation:** defer; item text is indexed later in a derived table at publication, without the content becoming rows |
| Q20 | A separate subdomain for the player document (such as `player.<domain>`) instead of relying on the opaque origin of the `sandbox` attribute alone | A second layer of isolation: a different origin means completely separate storage, cookies and policies, and protects against future configuration mistakes | Before the public launch, and certainly before community plugins open | **Recommendation:** the player address comes from the `PLAYER_ORIGIN` setting from now on (implemented in S2), and the subdomain is added when the final hosting is chosen (with Q12) |
| Q21 | Does a **content creator** make their own templates (not plugins) and share them? The studio became the Contributors' by R10, but a template is closer to a content creator's work than to a Contributor's | Templates are less risky than plugins and speed up authoring, but a shared template enters every creator's experience | When the first content creator asks for it (phase B) | **Recommendation:** personal templates for the content creator in phase B without sharing, then sharing with review |
| Q22 | The condition for direct publishing of a plugin by a non-verified Contributor: is a number of successfully reviewed plugins (say 3) enough to grant publishing without review, or does review remain until verification? | Manual review of every plugin is a burden on a single developer, and waiting discourages contributors | When the first real contributors arrive (phase B) | **Recommendation:** review for everyone in phase A, then a threshold of "3 reviewed plugins without a report" as a `platform_settings` setting in phase B, and verification removes the condition in phase C |
| Q24 | The channel for warnings and notifications from the administration to a member (R17 item 5): a message inside the platform (the `notifications` table that exists since S0 and a notifications page), an e-mail (needs a dedicated SMTP provider — Q14), or both? | "Send a warning to the owner of the attachment" in the case system (S4) is not built before the channel is chosen | With the design of S4 | **Recommendation:** the in-platform notification first (it does not depend on the limited free mailer), and e-mail once SMTP is available |
